# Clinime server operations

Node 22+ Netlify Request/Context function: `netlify/functions/api.mjs`. All state uses the private named store `clinime-private-v1`; no public Blobs links are generated. The only dependency is pinned `@netlify/blobs` 11.1.7. Resend uses Node fetch with a 10 second timeout; tests inject an in-memory store and mail transport and never send external mail.

Run from this project: `node --test tests/backend.test.mjs`.

## Configuration

- `PUBLIC_ORIGIN`: exact HTTPS origin, without trailing slash/path. Auth and all mutations require this exact Origin header.
- `APP_SECRET`: cryptographically random secret, at least 32 characters. It signs/HMACs identities, sessions and codes and encrypts temporary challenge replay material. Never expose it in public assets/logs. Changing it invalidates sessions and changes account identifiers; migration is required to retain account access after rotation.
- `RESEND_API_KEY`, `EMAIL_FROM`: verified sending configuration. A Resend API success means **accepted for delivery**, not verified inbox arrival. The public `emailStatus:'sent'` enum has this provider-acceptance meaning. Mail is always addressed to the verified immutable account email.
- `CLINIC_SCHEDULE_JSON`: required. Shape `{ "timeZone":"Asia/Riyadh", "weekdays":[0,1,2,3,4,5,6], "open":"10:00", "close":"18:00", "stepMinutes":30, "horizonDays":60 }`. Weekdays use UTC Sunday 0–Saturday 6 for the selected Gregorian date. All appointment timestamps are interpreted in Riyadh time. Missing/invalid schedule fails availability and new/moved reservations closed.

Root authorized the daily 10:00–18:00, 30 minute, 60 day window **for this experimental deployment's offered testing schedule** on 2026-10-28. It is not verified clinic opening hours. The operator must replace it with a verified resource schedule before a real clinic launch. There is one shared resource: `any` and `gigi` reserve the same resource, so neither label bypasses overlap checks.

Missing mail/secrets returns `emailEnabled:false` and does not activate a fallback login. No `123456` bypass, phone login or OAuth exists in this backend. Do not send development email except the human-authorized owner-address end-to-end check managed by Root.

## Atomicity, recovery and ownership

Root approved one strong-CAS clinic booking ledger instead of separate daily records. Every booking snapshot, resource interval and mutation receipt commits in the same conditional write. A cross-day reschedule cannot release the old interval before the new interval commits; a rejected new slot leaves the old booking unchanged. The ledger contains private ownership IDs; API responses filter by the authenticated account and strip ownership/fingerprint/internal mail fields. Availability exposes dates/slots only. Supplying `bookingId`/`excludeBookingId` for edit availability requires its owner session.

The adapter uses actual SDK `getWithMetadata(...,{type:'json',consistency:'strong'})`, `setJSON(...,{onlyIfNew:true})` or `{onlyIfMatch:etag}`, and checks `modified`. A missing response ETag fails closed. There are 16 bounded CAS attempts. Never replace these with read-then-write pseudo-locks. `STORE_UNAVAILABLE` can mean the commit acknowledgement was lost. The frontend must retry with the **same UUID requestId and identical payload**, not submit a fresh request. Create booking IDs are deterministically derived from account/request UUID, protecting duplicate creation beyond recent-receipt retention too.

Challenges last 10 minutes, allow 5 failed attempts, and consume code+link together through one CAS that also stores the session HMAC. Session cookies are HttpOnly/Secure/SameSite=Lax/Path=/ with 7 day expiry. CSRF is session-specific and returned from verify/me. Logout revokes server state. Only verified email sets account identity; profile name edits cannot change it.

No code/token is returned by auth-request or logged. The short-lived challenge stores HMACs and an encrypted replay envelope so an uncertain mail request can retry the identical provider payload/key. Consumption removes the envelope and hashes. Uncertain verify responses require requesting a new challenge if the original was consumed; silently reusing an already-consumed code is forbidden.

## Mail outcome and bounded retries

An auth request returns a challenge only after provider acceptance. Definite rejection is `EMAIL_UNAVAILABLE`; network/timeout/429/5xx ambiguity is `AUTH_DELIVERY_PENDING`. Retry its same request UUID. Both code and link are included in the same message; either consumes the challenge.

A saved booking remains saved if its confirmation mail is failed/pending. Transactional confirmations are unaffected by reminder preference. Owner-only confirmation retry reuses `booking/{id}/{revision}` and identical snapshot mail content. Resend retains idempotency keys 24 hours; this server stops automatic/explicit resend attempts at 23 hours from the revision's mail start time. Older pending/failed state remains visible for operator reconciliation. Do not create a fresh key to “fix” an unknown delivery without checking provider records; that may duplicate mail. A later booking revision intentionally gets a new notification key.

## Capacity, retention and maintenance

This single-clinic ledger is deliberately bounded: 5000 historical bookings, 10000 recent mutation receipts and 8 MiB serialized content. Reaching a limit fails closed with `SCHEDULE_CAPACITY`; it never drops bookings or silently prunes cancelled history. Mutation receipts older than 72 hours are removed during a successful new mutation. The last durable booking remains; an old create UUID cannot create a duplicate. Old update/delete requests whose receipts expired still must satisfy current revision, so stale replay cannot overwrite a later state.

This is a low-throughput single-resource implementation. CAS contention and full-ledger reads/writes grow with history; migrate reservations/history to a transactional database before materially increasing clinic/resource count or approaching these limits. Scale limits are safeguards, not production performance measurements.

No unattended cleanup function was added in this scope. Logical expiry is enforced on every challenge/session/rate check. The operator must establish housekeeping and a retention/privacy policy for private records:

- Remove expired unused auth records after a conservative grace period (at least 1 day after challenge expiry); retain active sessions until expiry/revocation. Remove expired session records after at least 1 day grace. Never inspect/export raw OTP tokens to do maintenance.
- Rate event arrays discard events outside their window on next access, but hashed per-IP/per-email bucket keys remain. Do not unconditionally delete an active limiter while requests may mutate it: the SDK has conditional writes but no conditional delete. Quiesce traffic or migrate/tombstone atomically under an approved maintenance procedure.
- Keep account and historical booking records until the agreed business/privacy retention policy authorizes deletion/export. This version provides logout, not an account-deletion API.
- Review provider pending mail that passes 23 hours and storage/capacity failures through private operator access. Do not expose admin diagnostics, store dumps, secret values or provider responses in customer API errors.

The unit/integration tests establish behavior against a deterministic conditional store, including concurrent intervals and lost acknowledgements. They do not establish live Netlify storage behavior, sender verification, inbox delivery or actual clinic fulfillment; Root must separately verify the authorized deployed journey.

## Loyalty and referrals (local review implementation)

The loyalty program lives inside the existing `clinic/booking-ledger-v1` strongly consistent CAS ledger. Booking creation atomically recomputes authoritative catalog prices and one promotion, consumes an owned single-use coupon or reserves a first-booking referral, and stores public subtotal/discount/payable snapshots without changing item prices. Cancellation releases the associated unused coupon/referral reservation; the original coupon expiry remains fixed. Staff checkout, receipts and emails use discounted payable. Added session services keep their frozen full prices and do not inherit the original booking discount.

Authenticated `GET /api/loyalty` enrolls an actual email-verified server session once and grants the configured welcome credit. An account created by reception is not email verification and receives no welcome credit before its owner signs in. Subsequent wallet reads, including point-expiry calculation, do not mutate the shared booking ledger. `POST /api/loyalty/quote` accepts `{items,code}`; `POST /api/loyalty/redeem` accepts a frozen `{requestId,revision,rewardId}`. Monetary-operation UUIDs and fingerprints are retained in loyalty requests so uncertain results can be retried after a coupon is spent. Replays return the same coupon with its current availability status.

`GET /api/admin/loyalty` and `POST /api/admin/loyalty` retain existing verified session, origin, CSRF and administrator authorization. POST actions are `adjust` (existing `userId`, nonzero integer `points` between -1,000,000 and 1,000,000, mandatory `reason`) and `rules-save` (full validated `rules`). Adjustments cannot overdraw available unexpired points. Credit/debit events and administrative audit records are append-only; debits allocate the oldest expiring credit first. Existing issued coupons keep their percent, cap, eligible service IDs and expiry when program rules change. Customer responses exclude friend identities/emails, medical information, receipt data and private coupon/referral associations.

Default configurable rules: verified-email welcome 200 points; one point per eligible net SAR paid (whole points rounded down); first paid completed visit 300; third paid completed visit 500; invited customer's first eligible booking 5% up to SAR75; referrer 500 pending until that visit finishes and is fully recorded as paid. Reward tiers are 5,000/5%/SAR75, 12,000/10%/SAR150 and 20,000/15%/SAR200. Points expire 12 calendar months after their individual credit (month-end clipped in UTC); reward coupons expire after 90 days by default. An empty eligible-service list includes all services. Discounts round down to halalas and never exceed eligible subtotal or their frozen cap. One promotion per booking; codes cannot stack. Self-referral and an earlier noncancelled eligible booking disqualify referral use; a wholly ineligible prior booking does not consume first-eligible-booking eligibility. Cancelling before completion frees first-booking referral eligibility.

Points are granted only inside a new staff transaction that closes a finished visit with actual receipts exactly covering its positive payable amount. Confirming a booking, submitting a form, starting/finishing a session without payment, partial payment, cancelled visits and zero-payable visits do not grant purchase or milestone points. Only eligible positive paid value counts toward purchase points and visit milestones. Wholly ineligible closures are still recorded as settled once and cannot receive retroactive awards after rule edits. Historical finished, closed and fully paid positive eligible visits count when positioning the new visit at milestone one or three, but no read/migration retroactively awards credits for those historical visits. A customer with a historical paid closure therefore does not receive a new first-visit bonus. Settled visit eligibility is frozen at settlement; pre-feature history uses current earning eligibility without retrocredit. The new third eligible completed visit can receive the third-visit bonus even when earlier visits predate the program.

This change is local and has not been deployed. Local automated tests use in-memory stores and fake delivery; they do not establish real payment-provider settlement or email delivery.

A referral reservation earns its pending credit only when its booking is the customer's first eligible finished and fully paid visit. If a different eligible visit settles first, the pending referral becomes `disqualified` with `reason: another-eligible-visit-completed-first` and `closedAt`; pending points drop to zero immediately, and closing the reserved booking later cannot award the referral. Customer pending-entry projections expose this status/reason without exposing the referred customer's identity. Booking discounts also freeze private proportional allocations across their original discount-eligible lines. Earning-rule changes intersect those allocations with earning eligibility, so a discount on an ineligible original service cannot reduce points for a different eligible service or a full-price session addition. Private allocations and settlement records remain outside customer/admin booking pricing projections.

## Care Point weekly challenge

`server/care-point.mjs` stores issued challenges, accepted solutions, weekly scores and frozen results in the separate strongly consistent `clinic/care-point-v1` ledger. The authenticated session owns each round. The server regenerates the canonical puzzle and verifies all sixteen rotations, immutable tiles, complete path, three flowers and the current Riyadh week before awarding 100 points once. No browser-local score is imported. Guest ranking exposes only the player-chosen first name, points and rank; account IDs, full names, email and clinical data stay private. A player explicitly chooses the public first name before starting; the value is normalized to its first word, validated as letters, and retained per account across weeks. Generated legacy aliases and generic participation labels are never projected. Unnamed legacy accounts retain their scores, rank and prize eligibility but are omitted from public name rows until they choose a first name. The public total counts all scored competitors; visibleTotal counts named public rows, and player.totalCompetitors supports the private standing summary. Changing the display name preserves existing scores, rounds, frozen leaders and prize records. Empty rankings contain no sample participants.

Customer endpoints are `/api/care-point/public`, `/api/care-point`, `/api/care-point/name`, `/api/care-point/start` and `/api/care-point/complete`. The name mutation uses a durable request ID and a separate per-account rate limit. Naming alone does not enroll a player or award points; previously issued legacy rounds remain completable while the next new start requires the public name. Mutations use the existing verified session, exact origin and CSRF checks. Durable request fingerprints and accepted-round markers recover duplicate or ambiguous requests; clients freeze pending requests and reconcile `lastCompletion` across reloads. Basic account request limits are abuse controls, not proof of human play. Published puzzle seeds and allowed hints mean automated solving remains possible; weekly prizes require owner review.

Care administration at `/api/admin/care-point` additionally requires `CLINIME_ADMIN_EMAILS` membership, even when the existing general staff workspace permits open verified-email enrollment. Verified owners and customers participate under the same current competition rule. Previously excluded owner points in an unfrozen week enter the standings immediately, without changing scores or round receipts. Already frozen historical eligibility, leaders and prize records stay unchanged. Administrative permission remains separate from gameplay eligibility. The admin `participants` collection additionally includes actual eligible players who started their first round and still have zero points. Public rankings and prize eligibility still count completed puzzles only; no page views or invented participants are added. The page refreshes on focus and visibility return and offers a manual refresh.

Weeks run Sunday 00:00 to the following Sunday 00:00 in Asia/Riyadh. `care-point-sweep` runs Saturday at 21:00 UTC and freezes ended standings only. It never chooses a tied winner or credits a prize. The marketing/contest page can pause/resume the challenge, finalize an ended week, resolve a tie once with a recorded cryptographic draw, and approve the fixed SAR100 prize. A stable `care-prize:<week>` financial marker and positive 10,000-cent `care-prize` wallet transaction commit together in the existing booking ledger; the separate game-ledger status reconciles safely after lost acknowledgements. Repeated approvals cannot issue another credit. These credits use the existing internal SAR wallet and do not create Wallet pass stamps or legacy loyalty points.

Current safeguards fail closed at 2,000 players or 20,000 issued rounds per week, 104 retained weeks, 5,000 chosen-name profiles, 100,000 command receipts or an 8MB serialized game ledger. No history is silently discarded. Monitor capacity and contention before expanding usage; these limits are not load-test results. Candidate eligibility and campaign rules remain operator responsibilities. No real prize was granted during local verification.

Owner-only `select-winner` can select an actual current-week participant before the deadline. It records a frozen financial selection, credits the fixed SAR100 once for that account, then sends the designed prize email. Gameplay remains available until the calendar deadline unless the challenge is explicitly paused; financial frozenAt records do not close play. Existing manually selected winners and credited awards remain unchanged when later scores arrive or the week ends. Distinct participants may receive separate manual awards, at most once per account per week; additional award and email identifiers are scoped by the selected account while the original award identifiers remain unchanged. Participant account details are restricted to the owner endpoint. Email delivery has a separate frozen receipt/provider key, short lease and a 23-hour retry window; pending/failed mail never reverses a credited prize. `retry-prize-email` only retries that receipt and cannot issue another credit.

Manual awards can be given to more than one distinct current-week participant. Each account is credited at most once per week. Existing primary prize/transaction/mail receipt IDs remain valid; additional recipients have separate durable award and mail receipt IDs. Awarding another participant preserves earlier awards and the existing competition closure state. Each email retry or interrupted-credit recovery identifies its recipient and cannot select or credit another account.
